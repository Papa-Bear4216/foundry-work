## 1. Executive Summary

## 2. What Should Be Cached? (`KEK` vs `MK` vs Derived Sub-Key)

Architecture sections 5.1–5.4 define the key hierarchy (`documented`, Section 7, `E-1`):

```text
passphrase ──scrypt(N=2^17,r=8,p=1..2,salt)──► KEK (32 B) ─┐
                                                           ├─ unwraps ─► MK (32 B)
recovery key ──HKDF(vault_id)───────────────► RK  (32 B) ──┘               │
                                                                           ├─► PK -> CK -> enc / id keys
                                                                           ├─► index key (per generation)
                                                                           ├─► signing seed (Ed25519)
                                                                           └─► keyring-mac / profile-label / tombstone keys
```

Four candidates were evaluated against the specification (`E-1`) for the cached value held in `KeyCache`:

| Candidate | Skips `scrypt` (`~128 MiB` algorithmic memory [`documented`, `E-2`], `204.42`–`377.94 ms` median at `p=1` [`measured` in V-0, `E-3`])? | Covers `search`, `import`, `verify --deep`? | Self-invalidates against current keyring on `change-passphrase`? | Self-invalidates against current keyring on `rekey --all`? | Exposes user's raw passphrase? | Verdict |
|---|---|---|---|---|---|---|
| Raw passphrase | No | Yes | Yes | Yes | **Yes** | **Reject** — still pays full KDF cost/memory and exposes reusable user secrets |
| `index` key only | Yes (for `search` only) | **No** (`import`, `verify --deep`, `rebuild`, signing fail) | No | Yes (index key rotated) | No | **Reject** — churns on every erasure/rebuild and still prompts on write/verify |
| Master key (`MK`) | Yes | Yes | **No** (`MK` is unchanged by `changePassphrase`) | Yes (`keyring.mac` fails) | No | **Runner-up** — survives `change-passphrase` against the current keyring if eviction fails or a stale cache blob is restored |
| **Passphrase-derived `KEK` (32 B)** | **Yes** | **Yes** | **Yes** (`kdf.salt` rotates; current `master.by_passphrase` GCM unwrap fails) | **Yes** (`kdf.salt` and `MK` both rotate) | **No** | **Recommended (if an OS adapter is later built)** |

### 2.1 Why `KEK` (bound to `vault_id` and `sha256(kdf.salt)`) wins over `MK`

1. **Same unlock scope as `MK` without skipping keyring authentication:** Caching the 32-byte `scrypt` output avoids running `scrypt` (measured for `p=1` only in [V0_MEASUREMENT_REPORT.md](V0_MEASUREMENT_REPORT.md) at `165.84 MiB` local Windows / `165.24 MiB` Windows CI / `177.56 MiB` Linux CI `maxRSS`, and `204.42 ms` local 16-core Windows / `344.86 ms` 2-core Windows CI / `377.94 ms` 2-core Linux CI median wall time, `E-3`; `p=2` is **`untested`**, `E-4`), while unlocking the full keyring (`index`, `collection`, `profile`, `signing`) via one AES-256-GCM unwrap of `master.by_passphrase` (unwrap latency **`untested`** in V-6, `E-4`) plus the standard `keyring.mac` check (`E-1`).
2. **Self-invalidating against the current keyring across passphrase changes:** Per `A-31` and `A-32` (`E-1`), `changePassphrase` generates a fresh 32-byte `kdf.salt`, derives a new `KEK`, re-wraps `master.by_passphrase` with the complete `kdf` object in its AAD, and leaves `MK` unchanged. If `MK` were cached and cache eviction failed (crash, permission error, or restored cache file), the stale `MK` would **still unlock the current keyring**. A stale `KEK` fails AES-256-GCM authentication against the **current** keyring's new `kdf` AAD and `master.by_passphrase` ciphertext, requiring the adapter/unlock path to zero and discard the cached `KEK`, attempt cache eviction, and fall back to interactive unlock while keeping every keyring and §5.7 withdrawal check (Section 8 item 6).
3. **Never caches the recovery key (`RK`):** The recovery-key unlock path (`master.by_recovery`) is an emergency path that **MUST** remain independent of `KeyCache` and **MUST NOT** populate the cache (Section 8 item 8).
4. **No bypass of v1 keyring verification:** Using a cached `KEK` **MUST** still authenticate the current keyring (`format`, `vault_id`, `kdf` bounds, `master.by_passphrase` slot AAD, and constant-time `keyring.mac`) before unwrapping any entry key (Section 8 item 6).

### 2.2 Erasure Interaction and Limits (Architecture §5.7)

Caching `KEK` interacts with erasure across three distinct specification cases (`documented`, `E-1`):

1. **Surviving KEK or restorable DPAPI blob + an old keyring copy:** Salt rotation (`change-passphrase` or `rekey --all`) invalidates a cached `KEK` **only against the current keyring's `master.by_passphrase` wrap**. If an old `KEK` survives or a previously backed-up/shadow-copied DPAPI blob is restored alongside a matching **old keyring copy** (carrying the earlier `kdf.salt`), that `KEK` can still unwrap `MK` in the old keyring and recover the collection or index keys that old keyring held before erasure. This matches Architecture §5.3 and §5.7 limit 1: neither passphrase changes nor cache eviction cryptographically revoke historical keyring copies.
2. **Profile or collection key destruction (`foundry erase` for a profile or collection, Architecture §5.7):** Destroying a profile or collection destroys the target profile/collection keys (and retired index key) in the working keyring (`wrapped: null`, `state: "destroyed"`) and appends `consent.withdrawn` / `key.destroyed`, making records under those keys unreadable once every keyring copy is updated. However, it does **not** rotate `kdf.salt` or `MK`. Consequently, if live-cache eviction fails during profile/collection key destruction, the cached `KEK` remains cryptographically usable against the **current** keyring for remaining active keys.
3. **Single-item redaction (`redaction.applied`, Architecture §5.7):** Erasing a single item appends `redaction.applied` (with its keyed tombstone), which **hides the item immediately** from all projections and read paths, **but does not destroy the collection key and does not rotate `kdf.salt` or `MK`**. The item's ciphertext remains cryptographically readable under the still-live collection key until `foundry vault rekey <collection>` re-encrypts remaining items under a fresh collection key and destroys the old collection key. An implementation must never report a redacted item's ciphertext as unreadable before collection rekey completes.

Accordingly, any future OS adapter and vault unlock path **MUST** enforce (Section 8 items 6–7):
- Every cache-assisted read **MUST** authenticate the current keyring and honour Architecture §5.7 withdrawal/redaction events (`consent.withdrawn`, `redaction.applied`, `key.destroyed`) and destroyed-key states (`wrapped: null`, `state: "destroyed"`).
- Each high-privilege and erasure operation — `change-passphrase`, `rekey --all`, profile/collection key destruction, single-item redaction (`redaction.applied`), and collection rekey (`foundry vault rekey <collection>`) — **MUST NOT** read from `KeyCache`, **MUST** require fresh interactive authentication (passphrase or recovery key), and **MUST** evict the live cache entry (reporting eviction failure explicitly rather than ignoring it).
- **Explicit limit (live-cache eviction vs old-copy destruction):** Evicting the live cache removes the active cache file or revokes the active kernel key, but a `KeyCache` adapter **cannot guarantee destruction of historical copies** of a Windows DPAPI cache blob retained in OS Volume Shadow Copies, Windows File History, backups, cloud sync, or flash storage blocks (Architecture §5.7 limits 1–2; `R-4`).

## 3. Windows: `os-protected` (Per-User DPAPI)

### 3.1 Binary, Spike Invocation Contract, and Production Gaps

- **OS binary (spike):** Windows PowerShell 5.1 (`System32\WindowsPowerShell\v1.0\powershell.exe`), shipped inbox on Windows 10 and Windows 11 (`documented`, `E-33`). PowerShell 7 (`pwsh.exe`) does not ship inbox (`documented`, `E-33`) and was not used.
- **What the spike does (`win-dpapi-spike.mjs` on branch `spike/v-6` at commit `3ba11ce`) — synthetic keys ONLY:**
  1. **Untrusted helper path resolution:** The spike constructs the helper path from the inherited `process.env.SystemRoot` (falling back to `C:\Windows`). An attacker or process able to override `SystemRoot` in the environment could redirect Foundry to a malicious executable that receives the `KEK` on stdin.
  2. **Unvalidated `protect` output:** The spike persists whatever `stdout` a successful `protect` invocation returns without validating that it is a genuine DPAPI ciphertext blob. A substituted or malfunctioning helper that echoes its input would cause plaintext `KEK` material to be written to disk.
  3. **Immutable string copies and incomplete error-path zeroing:** The spike passes `kek.toString('hex')` as a UTF-8 string over stdin/stdout (`encoding: 'utf8'`) and parses `$hex` / `[BitConverter]::ToString` in PowerShell, leaving immutable plaintext `KEK` copies in V8/Node strings and .NET managed strings that survive `Buffer.fill(0)` / `[Array]::Clear`. Additionally, `[Array]::Clear($bytes, ...)` is outside a `try`/`finally` block, so a parse or DPAPI error skips clearing `$bytes`.
  - All three shortcuts above are **acceptable only for the synthetic test keys in the spike**.
- **Production requirements (collected in Section 8 items 1–3):**
  - A production adapter **MUST** resolve the Windows system directory from a source the user environment cannot override — candidate mechanisms (**`untested`**, `E-32`) are Win32 `GetSystemDirectoryW` / `GetSystemWindowsDirectoryW` (`kernel32.dll`; not directly exposed by Node.js built-ins, so verifying zero-addon access is an open implementation item) or verifying the canonical resolved path (`fs.realpathSync`, rejecting symlinks/reparse points) against machine-owned registry metadata (`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\SystemRoot`, without using untrusted `SystemRoot`/`PATH` to query it), non-user-writable `SYSTEM`/`TrustedInstaller` ownership/ACLs, and Microsoft Authenticode signature verification.
  - A production adapter **MUST** refuse to spawn or send the `KEK` if the helper path does not resolve to that verified trusted path (failing closed to `none`).
  - A production adapter **MUST** validate `protect` stdout before persisting: strict base64/structure and length-bounds verification that the output is a well-formed DPAPI blob, plus an explicit check that neither the encoded output nor its decoded bytes equal or contain the plaintext `KEK` (raw, hex, or base64).
  - A production adapter **MUST** use bounded binary stdin/stdout pipes (`encoding: null` in Node; `[Console]::OpenStandardInput()` / `[Console]::OpenStandardOutput()` in PowerShell) and mutable byte buffers (`Buffer`/`Uint8Array` and `byte[]`) cleared in `finally` blocks on both sides, including every error path.
- **Process invocation arguments (spike):** `['-NoProfile', '-NonInteractive', '-NoLogo', '-OutputFormat', 'Text', '-EncodedCommand', base64Utf16LeScript]` with `shell: false`, `windowsHide: true`, and `timeout: 15_000` (spike configuration parameter; non-timeout is `measured` only for the 19 asserted `status === 0` calls in `E-24` and **`untested`** for the 4 failure calls in `E-28`).
- **Proposed production on-disk cache location (`untested`, `E-31`):** Machine-local `%LOCALAPPDATA%\Foundry\cache\<vault_id>.dpapi.json` — **never** `%APPDATA%` (Roaming), so cached blobs do not roam with Roaming User Profiles (`documented`, `E-33`). In the spike (`win-dpapi-spike.mjs`), the cache record was written under `tmpdir()` inside a temporary `foundry-v6-win-*` directory (`E-18`); `%LOCALAPPDATA%` storage was **not** exercised (`E-31`).

### 3.2 Mechanisms Evaluated

1. **Mechanism A — `[System.Security.Cryptography.ProtectedData]` (`DataProtectionScope.CurrentUser`):**
   - Loads precompiled GAC assembly via `Add-Type -AssemblyName System.Security` (per Microsoft documentation, loading an existing GAC assembly does not invoke `csc.exe`; `documented`, `E-33`).
   - Operates on `byte[32]` and passes UTF-8 `optionalEntropy = "foundry/key-cache/v1:<vault_id>:<kdf_salt_sha256>"`, which is documented by Microsoft to bind DPAPI decryption to matching entropy (`documented`, `E-33`). In the spike's changed-salt-hash wrong-entropy probe (call #15, which changed **only the salt hash** to `'0'.repeat(64)` while keeping `vault_id` unchanged), the exact predicate checked was `spawnSync` result `status !== 0 && !stdout.includes(syntheticKeyHex)` (`wrongEntropyRejected: true`, `measured`, `E-21`). Because `status !== 0` also holds when `spawnSync` returns `status: null` on timeout or launch failure (and neither `error` nor `stderr` was checked), it is **UNCONFIRMED** (`untested`, `E-28`) that PowerShell exited with a numeric nonzero status and **UNCONFIRMED** that DPAPI itself rejected the wrong entropy. Cross-vault rejection (changing `vault_id` in `optionalEntropy`) was not probed and is expected (`documented`, `E-33`) and **`untested`** (`E-28`).
   - **Constrained Language Mode (CLM):** In the spike's simulated CLM probe (call #16, `$ExecutionContext.SessionState.LanguageMode = 'ConstrainedLanguage'` followed by `Add-Type` and `ProtectedData::Protect` on a 4-byte literal), the exact predicate checked was `spawnSync` result `status !== 0` (`blockedInConstrainedLanguageMode: true`, `measured`, `E-22`). Because `status !== 0` also holds when `spawnSync` returns `status: null` on timeout or launch failure (and neither `error` nor `stderr` was checked), it is **UNCONFIRMED** (`untested`, `E-28`) that PowerShell exited with a numeric nonzero status and **UNCONFIRMED** that CLM caused the failure. Per Microsoft documentation (`documented`, `E-33`; real policy-enforced CLM **`untested`**, `E-32`), `Add-Type` and arbitrary .NET type invocation on `[ProtectedData]` are disallowed under CLM.
2. **Mechanism B — `ConvertTo-SecureString` / `ConvertFrom-SecureString` + `PSCredential`:**
   - Uses built-in `Microsoft.PowerShell.Security` cmdlets (`documented`, `E-33`, to call `CryptProtectData` with `CurrentUser` scope) and pipeline `$input`.
   - Single-run end-to-end round-trips succeeded under both `FullLanguage` (calls #17–#18, `measured`, `E-25`) and simulated `ConstrainedLanguage` mode (calls #19–#20, `measured`, `E-26`).
   - **Tradeoffs:** Does not support `optionalEntropy` (`documented`, `E-33`), produces a larger hex-encoded DPAPI blob (`716` hex chars `measured`, `E-25`; `358 B` raw `estimated` as `716 / 2`, `E-27`, vs `262 B` raw / `352` base64 chars `measured` for Mechanism A, `E-6`), inherently handles the key as immutable `.NET` strings via `-AsPlainText` and `GetNetworkCredential().Password` (`documented`, `E-33`), and had **no child working-set measurement**, no warm multi-run median, and no 1-bit tamper check in the spike (`untested`, `E-29`).

### 3.4 Secret-Exposure and Stderr Probes (Windows): Observed vs Untested

The spike (`win-dpapi-spike.mjs` on branch `spike/v-6` at commit `3ba11ce`) ran five narrow checks; **they do not establish zero exposure across all OS mechanisms**:

- **Observed in the spike (`measured`):**
  1. **Static `argv` and `env` lowercase-hex search (six direct Mechanism A `protect` benchmark calls only, `E-16`):** Only across the **six direct Mechanism A `protect` benchmark calls** (`i = 0..5`, calls #1, #3, #5, #7, #9, #11), the spike searched `args.join(' ')` and `JSON.stringify(env)` (for the allowlisted `env` object: `SystemRoot`, `WINDIR`, `SYSTEMDRIVE`, `TEMP`, `TMP`, `PATHEXT`, `COMSPEC`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`) passed to `spawnSync` for the synthetic key's lowercase hex string (`syntheticKeyHex`) only and found no match (`secretInArgvOrEnv: false`).
  2. **Empty trimmed stderr on non-instrumented benchmark pairs (`stderrCleanOnSecretPath: true`, `E-15`):** Checked `res.stderr.trim() === ''` across the **five non-instrumented Mechanism A benchmark pairs only** (`i = 0..4`: 5 `protect` + 5 `unprotect`, calls #1–#10).

## 4. Linux: `os-session` (Kernel Keyring via `keyctl`) — Untested Here

> **Testing status:** **Untested on Linux (`E-35`).** Per V-6 host constraints, WSL, Docker, and VMs were not started on this memory-constrained Windows machine. Analysis below is derived from upstream Linux `keyrings(7)`, `session-keyring(7)`, `user-session-keyring(7)`, `pam_keyinit(8)`, `keyctl(1)`, and distribution packaging documentation (`documented`, `E-36`; all Linux runtime behaviour is **`untested`**, `E-35`). Only syntax validation and the Windows non-Linux fail-to-`none` probe were executed (`measured`, `E-34`). The runnable verification script `linux-keyctl-spike.mjs` is committed in the spike scripts on branch `spike/v-6` at commit `3ba11ce` for the owner or Linux CI (`ubuntu-latest`) to run on real Linux.

### 4.1 Binary Availability and Conditional Dependency Status

Node.js has no built-in wrapper for the `add_key(2)` / `keyctl(2)` Linux syscalls (`documented`, `E-36`). Without a native addon and without a daemon, Node must spawn `/usr/bin/keyctl` (or `/bin/keyctl` on pre-usr-merge systems) from the `keyutils` OS package with `shell: false`.

A packaging distinction exists between the shared library (`libkeyutils1` / `keyutils-libs`) and the CLI package (`keyutils`) (`documented`, `E-36`; runtime **`untested`**, `E-35`):

| Distribution | `keyutils` (`/usr/bin/keyctl`) installed by default? (`documented`, `E-36`) | Notes |
|---|---|---|
| Fedora Workstation / Server, RHEL / Rocky / Alma | **Usually yes** | Pulled in by core auth/NFS/security package groups; absent on minimal container images |
| Ubuntu Desktop / Server, Debian | **Not guaranteed** | `libkeyutils1` is usually installed (dependency of `libkrb5-3`/PAM/systemd), but the CLI package `keyutils` is omitted on minimal, netinst, cloud, and container images unless pulled in by desktop/NFS/ecryptfs tasks or `apt install keyutils` |
| Arch Linux | **No** | In `core`, not part of the `base` metapackage (`pacman -S keyutils` required) |

**Dependency consequence:** "No new dependency" is **conditional** for Linux `os-session`. The design adds zero runtime *npm* dependencies, but it requires `keyutils` to be **already installed or installed as an extra OS package** (`E-36`). When `keyctl` is absent, Foundry must degrade cleanly to `none` (Section 8 item 14).

### 4.2 Command Contract, Unresolved Add-Before-Timeout Window, and Spike Gaps

- **NEVER use `keyctl add <type> <desc> <data> <ring>`:** passing `<data>` in `argv` exposes the raw key in `/proc/<pid>/cmdline` and `ps` (`documented`, `E-36`).
- **Stdin-only `keyctl padd` flow (`documented`, `E-36`; runtime **`untested`**, `E-35`):**
  1. **Store:** The spike script (`linux-keyctl-spike.mjs` on branch `spike/v-6` at commit `3ba11ce`) uses `keyctl padd user foundry:v1:<vault_id>:<salt_hash_16> @s` with raw 32-byte `KEK` written to `stdin` (`shell: false`, minimal `env: { PATH: '/usr/bin:/bin', LC_ALL: 'C' }`), returning numeric `<key_id>` on stdout. **The 16-hex-character salt-hash prefix (`<salt_hash_16>`) is synthetic-only:** two distinct salts with a matching 16-hex prefix would share the same Linux cache entry, allowing one context to replace or clear the other's entry (while current-keyring authentication would reject the wrong `KEK`). **Production requirement (Section 8 item 13):** production Linux lookup, storage, and eviction **MUST** bind to the **full** `vault_id` (32 hex chars) and **full** `sha256(kdf.salt)` (64 hex chars), e.g., `foundry:v1:<vault_id>:<kdf_salt_sha256>`.
  2. **Set kernel-enforced TTL:** `keyctl timeout <key_id> <ttl_seconds>`. In the spike script, if `timeout` fails, it runs `keyctl revoke <key_id>` and `keyctl unlink <key_id> @s`.
  3. **Read:** `keyctl search @s user <desc>` -> returns `<key_id>`; then `keyctl pipe <key_id>` -> writes the raw 32 bytes to stdout (never `keyctl print`, which hex-formats binary payloads per `keyctl(1)`, `E-36`).
  4. **Explicit clear:** `keyctl revoke <key_id>` followed by `keyctl unlink <key_id> @s`.
- **Unresolved feasibility condition — add-before-timeout window and partial-failure deadline gate:** `keyctl(1)` has no atomic `padd`-with-TTL subcommand (`documented`, `E-36`). If `keyctl padd` adds the key in the kernel and the helper dies or times out before returning `<key_id>` to Node, or if subsequent `revoke`/`unlink` cleanup fails after `timeout` fails, a key can remain in the keyring **without a kernel TTL**. **Logout teardown and description-based cleanup are NOT sufficient on their own:** if the helper dies after adding the key and cleanup fails, a long-running session could retain the `KEK` past the configured TTL. This race/failure window is an **unresolved feasibility condition**: the production gate **MUST** verify that the `KEK` becomes unreadable by the configured TTL deadline on partial failure (helper dies after add; cleanup fails), or refuse to ship the `keyctl`-CLI adapter (Section 8 item 12).
- **Spike script limitations (`linux-keyctl-spike.mjs` on branch `spike/v-6` at commit `3ba11ce`) — synthetic only:**
  - Key description truncates `kdfSaltHash` to 16 hex chars (`<salt_hash_16>`) instead of binding to the full 64-hex `sha256(kdf.salt)` (Section 8 item 13).
  - `get()` returns `null` on `keyctl pipe` failure without running the eviction/cleanup contract (`revoke`/`unlink`).
  - `get()` copies `Buffer.from(res.stdout)` without zeroing `res.stdout`, leaving an uncleared copy of the `KEK` in memory.
  - `clear()` treats any unsuccessful `keyctl search` lookup (non-zero exit status) as key absence (`null`) and ignores the results/exit codes of `keyctl revoke` and `keyctl unlink`. A policy, permission, or subprocess failure could therefore leave the key live in `@s` while `foundry lock` reports success, even with a corrected fallback wrapper.
  - All four gaps are acceptable only for the synthetic spike script; production requirements are listed in Section 8 items 10, 13, and 14.
- **Latency and memory:** **`untested`** (`E-35`; not measured on this host; any figures must come from running the spike script on real Linux CI and desktop sessions).
- **Secret exposure:** Expected not to appear in `argv`, `/proc/<pid>/cmdline`, `env`, shell history, or temp files (`documented`, `E-36`; **`untested`** here, `E-35`).

### 4.3 Session (`@s`) vs User Session (`@us`) vs User (`@u`) Semantics and Logout Gotchas

Per `keyrings(7)`, `session-keyring(7)`, `user-session-keyring(7)`, and `pam_keyinit(8)` (`documented`, `E-36`; all runtime behaviour **`untested`** here, `E-35`):

1. **Intended target (`@s`, `KEY_SPEC_SESSION_KEYRING`):** Created per login session by `pam_keyinit.so` and inherited across `fork`/`exec`. Destroyed when the last process holding a reference to that session keyring exits or PAM revokes it at session close (`E-36`).
2. **Gotcha A — `@s` fallback to `@us` and spike gap:** If a process has no explicit session keyring, accessing `@s` attaches the per-UID fallback `@us` (`user-session-keyring`), which is shared across all sessions of that UID and survives individual session logouts while any process for that UID remains (including `systemd --user` with `loginctl enable-linger`) (`E-36`). The spike script (`linux-keyctl-spike.mjs` on branch `spike/v-6` at commit `3ba11ce`) reports `distinctSessionKeyring` (`@s !== @us`) **but still writes to `@s` even when `@s == @us`** — acceptable only for the synthetic spike.
3. **Gotcha B — Distinct `@s` alone does NOT guarantee logout revocation:** Even when `@s !== @us`, a session keyring stays alive as long as any process or background service (such as `systemd --user` / `user@.service` or a detached daemon) retains a reference to it, or if PAM is not configured to revoke `@s` on session close (`E-36`). A production adapter **MUST** verify a session ring that is actually revoked at logout (distinct from `@us` and `@u`) before storing any `KEK`, and **MUST** refuse ambiguous or unverified setups by falling back to `none` (Section 8 item 11).
4. **Gotcha C — `systemd --user` keyring disconnect:** On modern desktops (GNOME/KDE), terminal servers launched under `systemd --user` can run in a different `@s` than an SSH login or another terminal (`documented`, `E-36`; **`untested`**, `E-35`).
5. **Gotcha D — Do NOT use `@u` (`user-keyring`) for `os-session`:** `@u` persists across logins while any UID process runs and does not meet Architecture §5.6's "gone at logout" contract (`documented`, `E-36`).
6. **Other failure modes (`documented`, `E-36`; **`untested`**, `E-35`):**
   - Containers / Flatpak / sandboxes: seccomp profiles commonly block `add_key(2)`/`keyctl(2)` with `EPERM` or `ENOSYS` -> `probe()` fails -> fallback to `none`.
   - Kernel quotas: default per-UID limits are `kernel.keys.maxkeys = 200` and `kernel.keys.maxbytes = 20,000` (`documented`, `E-36`; **`untested`**, `E-35`) -> `EDQUOT` on `padd` -> fallback to `none`.

## 6. Threat Statements, Expiry Semantics, and Fail-to-`none` Contract

### 6.1 Exact Threat Statements (Architecture Section 10)

| Adapter | Who can read the key while live? | Powered-off device threat | Disk persistence | Cache expiry enforcement |
|---|---|---|---|---|
| `none` (default) | **No reusable cache exists** (`measured` in spike `E-5`: `none` stores and returns no cached key). Per Architecture §10 (`E-1`), a live unlocked command still exposes key material and plaintext in process memory to an attacker or malware able to inspect that process while it runs | Protected by passphrase `scrypt` (`N=2^17`) + vault/index encryption (`E-1`) | None | Not applicable (no reusable cache) |
| `os-session` (Linux `keyctl` in `@s`) | **Any process running in the same Linux session keyring (`@s`) under the same UID** (or `root` / `CAP_SYS_PTRACE`) while the key has not expired (`documented`, `E-36`; **`untested`**, `E-35`) | Protected (kernel RAM only; gone at logout and power-off if `@s` is verified logout-revoked; `E-36`, `E-35`) | None (kernel RAM only, unswappable per `keyrings(7)`, `E-36`; `untested`, `E-35`) | **Kernel-enforced** via `keyctl timeout <id> <ttl>` (`EKEYEXPIRED` + kernel GC) and session teardown at logout (`E-36`) — **subject to passing the partial-failure deadline gate** for the `padd`-before-`timeout` window (logout/description cleanup is not sufficient on its own; Section 4.2, Section 8 item 12) |
| `os-protected` (Windows DPAPI `CurrentUser`) | **Any process running as the same Windows user account** (or local `SYSTEM`/Administrator with DPAPI backup key/impersonation) **until the cache file and any OS/backup copies are gone** (`documented`, `E-33`; **`untested`**, `E-32`) | **Weakened** (Architecture §10, `E-1`): survives reboot (`E-33`, `E-32`); offline security degrades to Windows account password / BitLocker rather than Foundry's passphrase | **Yes** — DPAPI ciphertext blob on disk (proposed production location: `%LOCALAPPDATA%`, `untested`, `E-31`; spike wrote under `tmpdir()`, `E-18`), possibly retained in shadow copies/backups/flash outside Foundry's control (`E-1`) | **Advisory only** — Foundry checks `advisory_expires_at_ms` and deletes expired files on read, **but** an attacker running as the user can call `ProtectedData.Unprotect` directly on an expired or restored blob before Foundry cleans it up (`E-33`) |

Note: Architecture section 5.6 (`E-1`) requires the wizard to state this plainly in one sentence before enabling either cache: *"Caching means anyone who can run code as the user can read the vault while the cache is live."* For Windows `os-protected`, the prompt must additionally disclose that the cached unlock **survives reboot** until explicitly locked/cleared, and that live-cache eviction cannot guarantee destruction of historical OS/backup copies of the cache file (Section 8 item 7).

### 6.2 How `none` Stays Default, Spike Wrapper Gaps, and Fail-to-`none` Contract

1. **Default configuration:** `KeyCache` defaults to `none` on every new vault and on every platform (`E-1`). Neither OS adapter is enabled automatically.
2. **Gaps in the spike scripts (`key-cache-port.mjs`, `win-dpapi-spike.mjs`, `linux-keyctl-spike.mjs` on branch `spike/v-6` at commit `3ba11ce`) — acceptable only for synthetic spike tests:**
   - **Unguarded diagnostics:** `createFailToNoneCache` invokes `onFallback` without `try`/`catch`, so a throwing callback can escape the wrapper and block the passphrase prompt; it also forwards raw `error.message` instead of fixed, non-secret reason codes.
   - **Incomplete Windows record validation:** `win-dpapi-spike.mjs` checks `record.advisory_expires_at_ms !== null && Date.now() > record.advisory_expires_at_ms`. A record with a missing (`undefined`), `NaN`, or non-numeric `advisory_expires_at_ms` (or missing/malformed `format`, `created_at_ms`, or `dpapi_blob_b64`) bypasses the expiry check and is still passed to `Unprotect`.
   - **Silent `clear()` / lock failures (wrapper and Linux adapter):** `createFailToNoneCache.clear()` catches and swallows deletion errors. In addition, `linux-keyctl-spike.mjs`'s `clear()` treats any unsuccessful `keyctl search` lookup as absence (`null`) and ignores `keyctl revoke` and `keyctl unlink` results, so a policy or subprocess failure on Linux could leave a key live while `foundry lock` reports success even with a corrected wrapper.
   - **Linux truncated salt prefix, read cleanup, and stdout buffer:** `linux-keyctl-spike.mjs` truncates `kdfSaltHash` to 16 hex chars (`<salt_hash_16>`), returns `null` on `keyctl pipe` failure without running the eviction/cleanup contract, and copies `Buffer.from(res.stdout)` without clearing `res.stdout`.
3. **Production fail-to-`none` contract (all collected as `MUST` requirements in Section 8):**
   - `probe()` returning `{ available: false }` disables caching and prompts for the passphrase (Section 8 item 4).
   - Diagnostics callbacks are guarded (`try`/`catch`) and receive only fixed, enumerated, non-secret reason codes; they can never block the passphrase prompt (Section 8 item 9).
   - On Windows `os-protected`, the complete cache record (including expiry presence, type, finiteness, and value, plus format/vault/salt/blob validation) is validated **before** invoking `Unprotect`; any malformed or expired record is evicted without calling `Unprotect` (Section 8 item 5).
   - On both Windows and Linux, `get()` returning anything other than an exact 32-byte `Buffer` (or failing during read/unprotect) zeroes any partial or raw stdout buffer, attempts eviction (`clear`/unlink/revoke), emits a fixed non-secret diagnostic, and returns `null` (cache miss) (Section 8 items 3, 9, 14).
   - If a cached 32-byte `KEK` unwraps from the OS cache (Windows DPAPI or Linux keyring) but **fails authentication against the current keyring** (e.g., `master.by_passphrase` AES-256-GCM unwrap failure due to a rotated `kdf.salt`/AAD or stale key, or `keyring.mac` mismatch), the adapter/unlock path **MUST** zero and discard the cached `KEK`, attempt eviction, emit a guarded fixed non-secret diagnostic, and fall back to interactive unlock (passphrase prompt), keeping every keyring (`format`, `vault_id`, `kdf` bounds, `master.by_passphrase` AAD, constant-time `keyring.mac`) and Architecture §5.7 withdrawal/redaction/destroyed-key check intact (Section 8 item 6).
   - A cache miss always falls back to interactive passphrase entry (`none`). It **never** opens the vault unencrypted, **never** skips `keyring.mac` / `master.by_passphrase` AAD / §5.7 withdrawal and destroyed-key verification, and **never** blocks passphrase or recovery-key unlock (Section 8 items 6, 8).
   - An explicit `foundry lock` / `clear()` **MUST** distinguish confirmed absence (no entry present -> idempotent success) from lookup failure (policy, permission, or subprocess error) and **MUST** verify revocation/removal succeeded before reporting success (reporting any failure explicitly) (Section 8 item 10).

## 8. Requirements for Any Future `os-protected` / `os-session` Adapter

Any future Codex package authorized to implement `os-protected` (Windows) or `os-session` (Linux) **MUST** satisfy all of the following requirements (and keep `none` as the permanent default):

1. **Trusted Windows helper resolution (no untrusted `SystemRoot`):** A Windows `os-protected` adapter **MUST** resolve the Windows system directory from a source the user environment cannot override (evaluating untested candidates in `E-32` such as Win32 `GetSystemDirectoryW`/`GetSystemWindowsDirectoryW` or `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\SystemRoot` plus canonical realpath, non-user-writable `SYSTEM`/`TrustedInstaller` ACLs, and Microsoft Authenticode verification) and **MUST** refuse to spawn or send the `KEK` if the helper path does not resolve to that trusted binary.
2. **Validate Windows `protect` output before persisting:** Before writing a cache file, the Windows adapter **MUST** validate that `protect` stdout is a well-formed DPAPI blob (valid base64, DPAPI envelope structure and bounded length) and **MUST** verify that neither the encoded string nor the decoded bytes equal or contain the plaintext `KEK` (raw, hex, or base64).
3. **Binary pipes and `finally`-cleared mutable buffers (no immutable KEK strings):** The production Windows path **MUST** transfer raw `KEK` bytes over bounded binary stdin/stdout streams (`encoding: null` in Node; raw standard streams in PowerShell) using mutable byte buffers (`Buffer`/`Uint8Array` and `byte[]`), and **MUST** clear those buffers in `finally` blocks on both sides, including all parse, length, and DPAPI error paths.
4. **Live capability probe on Windows:** `probe()` **MUST** exercise a real `protect`/`unprotect` round trip with a synthetic dummy value (through the verified helper path and output validation) before declaring `os-protected` available, and **MUST** fall back to `none` on any failure (including WDAC/AppLocker/GPO blocks where `powershell.exe` is present on disk, CLM restrictions, or DPAPI failures).
5. **Full Windows cache-record validation before `Unprotect`:** `get()` **MUST** validate the entire cache record schema — `format`, `vault_id`, `kdf_salt_sha256`, finite `created_at_ms`, strict type/finiteness/bounds on `advisory_expires_at_ms` (rejecting missing, `undefined`, `NaN`, or malformed expiry values and enforcing expiry), and valid blob encoding/length — **before** invoking `Unprotect`, and **MUST** evict malformed or expired records without calling `Unprotect`.
6. **Current-keyring authentication, cached-KEK auth fallback, and §5.7 erasure enforcement on every cached read:** Every cache-assisted unlock **MUST** authenticate the current keyring (`format`, `vault_id`, `kdf` bounds, `master.by_passphrase` AAD, constant-time `keyring.mac`) and **MUST** honour Architecture §5.7 withdrawal/redaction events (`consent.withdrawn`, `redaction.applied`, `key.destroyed`) and destroyed-key states (`wrapped: null`, `state: "destroyed"`). If a cached `KEK` unwraps from the OS cache but fails authentication against the current keyring, the adapter/unlock path **MUST** zero and discard it, attempt eviction, and fall back to interactive unlock, keeping every keyring and withdrawal check.
7. **High-privilege and erasure commands bypass cache and evict live entries:** Each of `change-passphrase`, `rekey --all`, profile/collection key destruction, single-item redaction (`redaction.applied`, noting that redaction hides immediately while ciphertext remains readable under the still-live collection key until collection rekey per Architecture §5.7), and collection rekey (`foundry vault rekey <collection>`) **MUST NOT** read from `KeyCache`, **MUST** require fresh interactive authentication, and **MUST** evict the live cache entry (propagating eviction errors clearly). Documentation and wizard prompts **MUST** state as an explicit limit that live-cache eviction cannot guarantee destruction of historical copies of a DPAPI cache blob in OS shadow copies, file history, backups, or flash storage.
8. **Independent recovery unlock:** Recovery-key unlock (`master.by_recovery`) **MUST** remain completely independent of `KeyCache` and **MUST NOT** populate the cache.
9. **Guarded, fixed non-secret diagnostics:** Diagnostic callbacks (`onFallback` / logging) **MUST** be wrapped in `try`/`catch` so they **MUST NOT** throw out of the cache wrapper or block interactive passphrase entry, and **MUST** emit only fixed, enumerated, non-secret reason codes (never raw subprocess output or arbitrary error strings).
10. **Explicit `lock` failure reporting and verified revocation/removal:** An explicit `foundry lock` (or `clear()`) **MUST** distinguish confirmed absence (no cached entry present -> idempotent success) from lookup failure (policy, permission, or subprocess error), **MUST** verify that revocation/unlink (Linux) or file deletion (Windows) actually succeeded before reporting success, and **MUST** report any lookup or deletion/revocation failure explicitly to the caller/user.
11. **Linux verified logout-revoked session keyring:** A Linux `os-session` adapter **MUST** verify that the target session ring is actually revoked at logout and distinct from `@us`/`@u` before storing any `KEK`, and **MUST** refuse ambiguous or unverified keyring setups (degrading to `none`).
12. **Linux add-before-timeout partial-failure deadline gate:** A Linux `os-session` adapter **MUST** treat the non-atomic `keyctl padd` -> `keyctl timeout` window as an unresolved feasibility condition. Logout teardown and description-based cleanup are **not** sufficient on their own (if the helper dies after adding the key and cleanup fails, a long-running session could retain the `KEK` past the configured TTL). The production gate **MUST** verify that the `KEK` becomes unreadable by the configured TTL deadline on partial failure (helper dies/times out after add; cleanup fails), or refuse to ship the `keyctl`-CLI adapter.
13. **Linux full `vault_id` and full salt-hash binding:** Production Linux `os-session` storage, lookup, and eviction **MUST** bind to the **full** `vault_id` (32 hex chars) and **full** `sha256(kdf.salt)` (64 hex chars). The spike's 16-hex salt-hash prefix (`foundry:v1:<vault_id>:<salt_hash_16>`) is synthetic-only and **MUST NOT** be used in production (distinct salts sharing a 16-hex prefix would collide on the same Linux cache entry, allowing one context to replace or clear the other's entry, even though current-keyring authentication would reject a wrong `KEK`).
14. **Linux OS package handling, read-failure cleanup, and stdout buffer zeroing:** A Linux `os-session` adapter **MUST** treat `keyutils` as an optional external OS package (failing to `none` when absent), **MUST** apply the same fail-closed cleanup/eviction contract on read failures as Windows, and **MUST** zero the original `keyctl pipe` stdout buffer (`res.stdout`) in `finally`.
15. **Implementation-package verification gates (`A-26`):** Before shipping either OS adapter, CI and platform verification **MUST** measure controlled cold-host timings (`E-11`) and full-command process and process-tree peak memory against Architecture §9 ceilings on pinned Node `24.22.3` (`E-30`), inspect `argv`/`env`/stderr on the actual adapter and failure paths (`E-15`, `E-16`, `E-31`), verify numeric nonzero exit and DPAPI/cross-vault rejection (`E-28`), test `%LOCALAPPDATA%` storage, transient temp-file activity, and byte-for-byte history equality (`E-31`), verify real Windows policy environments (CLM, WDAC/AppLocker, logging/transcription) and lifecycle cases (logout, reboot, admin password reset, roaming profiles; `E-32`), and execute real Linux CI and desktop session tests (`E-35`).

## 9. Recommendations and Conditional Scope for a Future Codex Package

1. **`none` adapter + `KeyCache` port contract — Build in `V-7` (CLI):**
   - Define the minimal `KeyCache` interface (`probe`, `get`, `set`, `clear`) and ship only `none` (`E-5`) as the Phase 1 implementation, keeping the thin slice free of platform-specific cache complexity and external OS-binary assumptions.
2. **`os-protected` (Windows DPAPI) — Build later (opt-in, Phase 2 / `P-5` or dedicated follow-up):**
   - **Why later:** The spike demonstrated synthetic DPAPI round-trips without a daemon or new npm dependency (`E-6`), but Phase 1 has no wizard to present the mandatory Architecture §5.6/§10 warnings (`E-1`, including reboot persistence and old-copy limits), production hardening requirements (Section 8 items 1–10, 15) are not yet designed/tested, and controlled cold-host timings (`E-11`), full-command ceilings on pinned Node `24.22.3` (`E-30`), policy/lifecycle cases (`E-32`), and Smart App Control (`D-22` / `P-6`) remain untested.
   - **Conditional design preference if later authorized:** Prefer Mechanism A (`ProtectedData` + `optionalEntropy` over `vault_id` and `sha256(kdf.salt)`, `E-33`) over binary pipes with trusted helper resolution, ciphertext validation, and live capability probing, degrading cleanly to `none` under Constrained Language Mode rather than maintaining a second `ConvertFrom-SecureString` path without `optionalEntropy` (`E-33`).
3. **`os-session` (Linux `keyctl`) — Build later (opt-in, conditional on Linux verification and feasibility gates):**
   - **Why later:** RAM-only kernel-TTL storage is the strongest documented caching model (`E-36`), **but** it is completely untested on Linux (`E-35`), depends conditionally on the `keyutils` OS package (`E-36`), requires verified logout-revoked `@s` semantics and full `vault_id` + full salt-hash binding, and requires passing the partial-failure deadline gate for the `padd`-before-`timeout` window (Section 8 items 11–15).
   - **Prerequisite before any authorization:** Run `linux-keyctl-spike.mjs` (from the spike scripts on branch `spike/v-6` at commit `3ba11ce`) on real Linux CI (`ubuntu-latest` with `keyutils` installed) and on a desktop Linux session with `systemd --user`, and produce a design addressing Section 8 items 11–14.
4. **macOS — Do not build in v1 (`D-5`, `E-37`, `E-38`).** Re-evaluate in `X-7`.

### Conditional Scope for a Future Codex Package (Proposed `A-34`, Not a Commitment)

If the owner later authorizes implementing `os-protected` and/or `os-session`, a future Codex work package would need to:
1. **`packages/vault` (small additive API, if authorized):** Add an internal or exported `{ kek: Buffer }` unlock path (e.g., `unlockByKek`) in `packages/vault/codec/src/keyring.ts` and `keys.ts` that would still enforce `kdf` bounds, `master.by_passphrase` AAD, constant-time `keyring.mac`, and §5.7 destroyed-key/withdrawal rules (with the caller discarding/zeroing any cached `KEK` that fails current-keyring authentication, attempting eviction, and falling back to interactive unlock while keeping every keyring and withdrawal check), plus a helper returning the derived 32-byte `KEK` on passphrase unlock so the CLI could pass it to `KeyCache.set()` and immediately zero its local copy. `changePassphrase`, `rekeyAll`, `erase`, and recovery-key unlock would remain strictly interactive / independent of `KeyCache`.
2. **CLI / Wizard (`V-7` / `P-5`, if authorized):** Provide `foundry lock` (reporting deletion/revocation failures distinctly from misses), a `--no-cache` flag, explicit opt-in configuration (default `none`), and the one-sentence warning (plus reboot-persistence and old-copy-limit disclosures on Windows).
3. **CI and verification gates on pinned Node `24.22.3`:** Implement every requirement and gate in Section 8, including controlled cold-host timings, full-command `A-26` memory ceilings, real policy/lifecycle checks on Windows, and real Linux CI/desktop tests (with `keyutils` present and absent, including the partial-failure deadline gate).
